> 本次实测**修正了设计稿 v0.1 中 4 处与真实 API 不符的地方** —— 这正是 M0 的价值。

## 一、假设 #2：DSH 的工具/审批 API 签名 —— ✅ **完全验证**

原以为要从文档推断，实际可以**直接读类型声明**（DSH 安装包里带 `.d.ts`）。
读完之后发现 v0.1 的骨架**有两处会直接跑不起来**。

### 1.1 ✅ 核实到的准确签名

```ts
// ① 工具注册
ctx.tools.register(definition: ToolDefinition): () => void

// ② ToolDefinition —— output 是必填！
interface ToolDefinition extends ToolSchema {
  readonly output: ToolOutputDefinition;        // ★ v0.1 漏了，会注册失败
  execute(args: unknown, exec: ToolRunContext): Promise<unknown>;
  timeoutMs?: number;                          // 协作式超时，必须转发 exec.signal
  presentCall?(args: unknown): ToolCallView | undefined;      // 纯函数，重放时也会被调用
  presentResult?(args: unknown, result: ToolResult): ToolResultView | undefined;
  isConcurrencySafe?(args: unknown): boolean;  // 只有 true 才加入并行组
}
interface ToolOutputDefinition {
  schema: JsonSchemaNode;                                    // 校验 execute 的返回值
  render(args: unknown, value: JsonValue): ContentBlock[];   // → 模型可见内容
  presentationMeta?(args: unknown, value: JsonValue): JsonValue;
}

// ③ 执行上下文
interface ToolExecutionInput {
  readonly callId: CallId;      // 必有
  readonly name: string;
  readonly arguments: unknown;  // 冻结的、经 lossless JSON 物化的参数
  readonly agent?: Agent;       // ★ 可选！可能为 undefined
  readonly signal: AbortSignal; // 必有，必须观察或转发
}

// ④ 审批请求 —— 只有五个字段
interface ApprovalRequest {
  readonly agent: Agent;         // 必填
  readonly toolName: string;     // 必填
  readonly callId?: CallId;
  readonly reason?: string;      // ★ 唯一的自由文本通道
  readonly signal?: AbortSignal;
}
type ApprovalOutcome = 'allowed-once' | 'rejected' | 'cancelled' | 'unavailable';
```

证据位置（均在 DSH 安装包内）：
- `dsh-tools/lib/types/index.d.ts` 第 97-172 行（ToolDefinition）、196-283 行（执行上下文）、603 行（register）
- `dsh-tools/lib/types/presentation.d.ts` 第 41、130 行（渲染意图）
- `dsh-user-approval/lib/types/index.d.ts` 第 104-125 行（ApprovalRequest）、141-171 行（ApprovalService）
- `dsh-user-approval/lib/types/types.d.ts` 第 23 行（ApprovalOutcome）
- `dsh-llm/lib/types/types.d.ts` 第 39-89 行（ContentBlock）

### 1.2 🔧 由此修正的设计（v0.1 → v0.2）

| # | v0.1 的错误 | 事实 | 修正 |
|---|---|---|---|
| 1 | 插件骨架的 `ctx.tools.register({name, description, parameters, execute})` 没有 `output` | `output` 是**必填**，含 `schema` 与 `render` | 全部工具补上 `output:{schema,render}`；`render` 用真实返回值驱动测试 |
| 2 | 把 `title/risk/target/impact/argv/rollback` 传给 `ctx.approval.request` | 这些字段**不存在**，审批请求只有 5 个字段 | 富 plan 改由 **`execute` 返回值 + `presentCall` 渲染**承载；审批只带一句精炼 `reason` |
| 3 | 未意识到 `exec.agent` 是可选的 | `agent?: Agent` | 需审批但无 `agent` 时**直接 blocked**（fail-closed），不静默放行 |
| 4 | 未意识到审批需要 open turn | `request()` 在空闲回合会被拒 | 记录为设计约束：**定时任务不能申请审批，只能做 R0/R1** |

### 1.3 💡 修正后的一个正面结论

第 2 条修正**反而强化了原设计**：既然审批请求承载不了富信息，那么
**必须先把 plan 作为一次独立工具调用返回，用户才看得到它，然后才谈审批** ——
这正是 §3 D7（check 先于 apply）要的效果。原来的设计意图对，实现路径错了。

### 2.3 ❌ 仍差最后一步（需你点头）

`--dump-config` 只证明**配置树合成成功**，**不证明模块被真的 import 了**。
要验证最后一步，需要一个真实启动：

- 启动 `dsh --profile web` 会与你**正在使用的** GUI 争 3080 端口 → 按规矩不擅自启动；
- 备选：另建一个独立 profile（`--profile vmprobe-dev`）来跑，不影响你的实例。

**因此 M0 剩下唯一未闭环项**：Loader 是否接受绝对路径 / `link:` / `file:` 形式的本地插件 `name`。
（模块本身可正常 import —— 见下节，`verify-plugin.mjs` 就是一次真实 import。）

## 三、假设 #3：`ssh2` 可安装性 —— ⏳ **未测**（M1 首项）

M0 没有传输层代码，因此未引入 `ssh2`。已确认的替代事实：

- 本机**已装 OpenSSH 客户端**：`C:\Windows\System32\OpenSSH\ssh.exe`、`ssh-keygen.exe`
- 已装 Git for Windows，含 `bash.exe`（可用于脚本语法检查 —— 已用）
- profile 是 pnpm workspace，加依赖形式为 `dsh plugin --profile web add ssh2`

⚠️ 注意：OpenSSH 的存在**不改变 D2 的结论** —— `ssh.exe` 仍无法非交互接收密码，
所以密码引导这一步依然需要 `ssh2`（或在 Windows 上引入 `plink.exe`，多一个依赖）。

### 4.3 三条值得单独指出的断言（都是被实测抓出来的真问题）

1. **拒密是机制而非自觉**：`assertSecretFree()` 在**写路径上**拦截敏感键名与 PEM 私钥内容，
   且有单测。写带 `password` 的对象会抛错，且**不改动已有数据**（先校验后落盘）。
2. **不让模型自我降级权限**：`system.update` 在检测到 `kernelUpgradePending` 时，
   风险级从 R1 **被迫**提升到 R2 并要求审批 —— 调用方（含模型）无法指定或降低风险级。
3. **不为做不到的事浪费用户审批**：
   `vmprobe_action` 的顺序是 `blocked → noop → 能力检查 → 审批 → 执行`。
   验证脚本断言：传输层未接线时，**审批调用次数必须为 0**。

### 4.4 一个被测试抓出的代码 bug（已修）

`decideApproval()` 最初对 R0/R1 也生成 `approvalReason` 字符串。测试断言它应为空后修正了**代码**：
留一个现成的 reason 会诱使调用方在无需审批时也去发起审批请求。
顺带修了一处**测试自身**的错误断言（用 `/password/i` 匹配整个文件，误伤了
`authRef.kind` 的**值** `"password"` —— 守卫只查键名是对的，测试改成只匹配键形式）。

### 4.5 另一个被实测抓出的兼容性问题（已修）

`agent/bootstrap.sh` 在**非 Linux** 环境（Git bash on Windows）运行时，
`/etc/os-release`、`systemctl`、包管理器全都不存在。
按「探测项独立容错、绝不整体失败」的原则实现后，脚本输出**合法 JSON**，
所有缺失项如实记为 `""`/`null`，而不是崩溃或编造值 —— 这正是 `probe.facts` 需要的降级行为。

## 五、M1 建议的首批任务

1. **闭环假设 #1 的最后一步**：用独立 profile 验证 Loader 真能加载本地插件（需你同意）。
2. **传输层**：引入 `ssh2`，实现连接复用 + keepalive + SFTP 推送；`probe.facts` 接真机。
3. **免密切换事务**：按 §8.2 实现，重点是「先另开连接验证成功才切断旧连接」的不变量 + 破坏性测试。
4. **`vmprobe_facts` 工具**：传输层就绪后暴露；同时把 facts 落盘到 storage。
5. **客户端插件**：先做 `conversation.session.header.actions` 连接状态徽标（最小可用 UI）。
6. **`ssh2` 安装验证**：`dsh plugin --profile web add ssh2`。
